# 合规规则引擎 · 个保法「单独同意」场景

把《个人信息保护法》中「单独同意」相关的判定，做成**可核验、可回溯、可测试**的规则引擎。

**当前版本（v0.1 / v0.2）的判定层用纯规则、不调用大模型**——因为判定必须确定、可复核、可回溯到法条原文，不能靠概率。

**自然语言 → 结构化字段的抽取层，计划由大模型承担（v0.3，尚未实现）**：
> **LLM 负责理解，规则负责判定，两者不混。**
> 这样即使换了模型、换了版本，判定结论仍然可复现。

> 🔗 **在线演示**：https://tina-6688.github.io/pipl-separate-consent-engine/
> （单文件静态页，零依赖；也可本地双击 `demo.html` 打开）

| 项 | 数量 |
|---|---|
| 规则 | **8 条**（覆盖第 13 / 17 / 23 / 25 / 29 / 30 / 39 条） |
| 字段 | **33 个** |
| Golden case | **15 个**（正例 / 反例 / 例外 / 叠加去重 / 边界） |
| 校验断言 | **92 项**，分 10 类检查，一条命令跑完 |

---

## ⚠️ 先说清楚它不是什么

- **不是法律意见。** 规则是对法条的**工程化建模**，法律正确性需专业律师复核；
  本仓库的自动校验只能证明**内部一致性**（规则 / 用例 / 引文 / 文档互相对得上），**不能证明法律判断正确**。
- **不是通用产品。** 只覆盖一个场景（个保法「单独同意」）的 8 条规则，规模很小。
  它的价值在**方法**：同一套「规则 + 三态输出 + golden case + 逐字引文校验」可以复制到别的法规。
- **Golden case 与规则集共享同一套假设**，因此可能同错——它防的是回归，不是法律错误。

## 三个核心设计

### 1. 三态输出（不是二值）

| 状态 | 条件 | 含义 |
|---|---|---|
| `not_applicable` | `存在个人信息处理行为 == false` | 明确不适用（第四条），确定结论 |
| `evaluated` | 至少一条规则触发 | 输出义务、缺失项、不适用清单 |
| `uncovered` | 无规则触发或字段不足 | **转人工，禁止默认判为合规** |

**第三条是底线**：规则集覆盖不到的场景，不能悄悄返回「合规」。

### 2. 三值逻辑（字段缺失 ≠ false）

条件求值结果只有 `True / False / None`。

- 字段缺失 → `None`（未知），**不当作 False**
- 所有条件都因字段缺失而无法判定 → 落到 `uncovered`，转人工

**为什么重要**：如果缺失当 False，那么「没提供任何信息」会被判成「没有触发任何规则 → 合规」。这是最危险的失败模式。

自检里专门验了这条：`空输入不判合规`。

### 3. 触发与履行分离

```yaml
condition:              # 决定「这条规则适不适用」
  all:
    - field: 对外提供
      operator: equals
      value: true

action:                 # 决定「合规不合规、缺什么材料」
  - type: obligation
    id: notice_recipient
    mode: all
    options:
      - field: 已告知接收方名称或姓名
        missing_label: 接收方名称或姓名
```

**如果不分离**，那么「已取得同意」时规则会直接消失——用户看不到「你是靠但书才合规的」。

## 去重规则（引擎已实现）

### 单独同意的要求强于一般同意（**单向蕴含**）

```
已取得单独同意  ⇒  视为已满足第13条的一般同意     ← 成立
已取得一般同意  ⇏  视为已取得单独同意            ← 不成立
```

**判据**：单独同意的**构成要件**更多（要「单独」，法定情形下还要「书面」），所以**要求**上更强；
但正因为要求更多，能**满足它的场景反而更少**。

> ⚠️ 注意：不要写成「单独同意 ⊃ 一般同意」——
> 如果按「满足的场景集合」读，方向正好是反的。只有**要求**的包含关系才成立。

**反向不成立的证据是 S2**：一般同意有、单独同意没有 → 第 25 条禁止**仍然成立**。

引擎在 `Engine.derive()` 里做这条推导：

```python
if 已取得单独同意 is True and 已取得个人同意 is not True:
    已取得个人同意 = True      # 并在输出里注明推导过程
```

**为什么必须做**：否则输入 `{单独同意: true, 一般同意: false}`（矛盾输入）时，
引擎会同时输出「PIPL-13-01 缺个人同意记录」和「PIPL-25-01 但书成立」——**自相矛盾**。

### 缺失清单去重

```
PIPL-23-01:separate_consent  未满足
PIPL-29-01:separate_consent  未满足
        ↓ 缺失清单去重（按 missing_label）
缺失材料：1. 单独同意记录          ← 只出现 1 次
```

基线规则 `PIPL-13-01:legal_basis` 在此时标记为 `subsumed`，不重复输出。

**验证用例：S10**

### 告知按对象分层，不跨维度去重

| 维度 | 来源 | 内容 |
|---|---|---|
| 处理者 | 第 17 条 | 处理者身份、目的方式种类保存期限、行权方式 |
| 接收方 | 第 23 条 | 接收方身份与联系方式、接收方的目的方式种类 |
| 境外接收方 | 第 39 条 | 境外接收方身份与联系方式、目的方式种类、向境外接收方行权的方式和程序 |

**两层说的是不同对象**（「你是谁」 vs 「接收方是谁」），所以都要列。

**验证用例：S4**（12 项 = 接收方 5 项 + 单独同意 1 项 + 境外接收方 6 项）

### 但书成立时规则仍要出现

**PIPL-25-01** 在「已取得单独同意」时不构成违法，但**规则必须输出并标注「依第二十五条但书」**，不能因合规而消失。

**验证用例：S6**

## 演示页（v0.2）

### 设计原则：判定逻辑只有一份

```
build_demo.py
   ├── 读 rules/*.yaml
   ├── 读 cases/golden_cases_v1.1.json
   ├── 用 engine.py 跑一遍（Python 算好所有结果）
   └── 输出 demo.html（把结果作为 JSON 内嵌）
             ↓
        HTML 里的 JS 只负责「渲染」，不含任何判定逻辑
```

**所以不会出现「第二套实现漂移」**——页面显示的就是引擎算出来的。

### 页面能看到什么

| 区块 | 内容 |
|---|---|
| 左侧 | 15 个场景，**按类型分组显示组标题**，颜色点表示结论 |
| 输入事实 | 该场景实际提供了哪些字段、值是什么 |
| 触发的规则 | 每条规则 × 每个义务组的状态（满足/未满足/已去重/条件未成立）+ 缺失项 |
| 缺失材料清单 | 去重后的完整列表 |
| **未触发 / 未判定的规则** | **可展开，逐条列出条件字段的期望值、实际值、判定结果** |
| 依据条文 | 触发规则对应的法条原文（逐字），**含 supporting_quotes**（如第 13 条规则同时展示第 17 条） |
| 引擎说明 | 推导过程、去重说明、字段不足提示 |

**「未触发也要能解释」是 v0.2 的验收标准之一。**
引擎为此输出 `inactive_detail`，区分两种原因：

- `condition_false` —— 字段提供了但对不上
- `field_missing` —— 触发字段没提供，无法判定

**响应式**：宽度 ≤ 860px 时左右布局改为上下；≤ 480px 时列表改为单列。**但未经真机验证**（见下文「校验的盲区」）。

### 为什么要做成静态 HTML 而不是 Streamlit

| | 静态 HTML | Streamlit |
|---|---|---|
| 别人能不能看 | **双击就开** | 需要装 Python + streamlit |
| 发给面试官 | **能** | 不能 |
| 自由输入 | 只能点预设场景 | 可以 |
| 离线 | **可以** | 需要本地服务 |

**结论**：静态 HTML 用于「给别人看」，Streamlit 留给「自己深挖」（v0.2b，未做）。

### demo.html 要不要提交到仓库

**要。** 它是交付物（能直接发人），但也是构建产物（可能过期）。

**validate.py 第 8 项会比对「页面内嵌的完整 result 对象」与「现跑一遍引擎的结果」（逐字段深度比较，不只摘要字段），不一致就报错。** 所以忘了重新生成会被抓住。

## 校验：一条命令

```bash
python validate.py
```

**退出码 0 = 全过；1 = 有问题**（可直接接 CI）。

### 十项检查

| # | 检查项 | 内容 | 断言数 |
|---|---|---|---:|
| 1 | **结构** | 必填字段、rule_id 唯一、枚举合法、各 condition 模式的 operator、三态契约 | 4 |
| 2 | **引文** | 每条 quote 必须是法条原文子串（B 级归一化）+ 归一化模块自测 5 项 | 16 |
| 3 | **yaml_audit** | 外部工具；返回码非 0 或 `errors>0` 都报错；工具缺失记 SKIP | 2 |
| 4 | **表对照** | 规则 **ID 集合**、触发/履行/quote、**rule_type**、**action.type** 五项一致 | 9 |
| 5 | **md同步** | 两份规则文件**逐条内容完全相等** | 9 |
| 6 | **用例** | 15 个 golden case 的实际输出 vs 期望（按 action_id 断言） | 16 |
| 7 | **边界** | 三值逻辑、字段推导、去重、但书、分层告知 | 10 |
| 8 | **演示页** | HTML 结构、数据与引擎逐字段一致、依据含附加引用、原因追踪完整 | 19 |
| 9 | **渲染** | node + 最小 DOM 桩真跑一遍 buildNav/showCase | 3 |
| 10 | **覆盖度** | 判「合规」者必须完整判定（陷阱1）；每个 action 至少被走到一次（陷阱5） | 4 |

> 第 10 项防的是两类最危险的问题：①**判了「合规」但其实没判定完整**；②**某条规则的某个分支从未被执行过**（死代码风险）。

### 常用参数

```bash
python validate.py --only 引文          # 只跑某一项
python validate.py --skip yaml_audit    # 跳过外部依赖
python validate.py -v                   # 打印细节
```

检查项名：`结构` `引文` `yaml_audit` `表对照` `md同步` `用例` `边界` `演示页` `渲染`

### 校验器自己也要被校验

**「全部通过」可能是真没问题，也可能是检查根本没生效。**

所以有 `test_validator.py`：对各检查项构造一个确定性破坏，**要求它必须 FAIL**。

```bash
python test_validator.py
```

运行后**直接打印结果**（同时写入 `test_validator_report.txt`）：

```
PASS P1-1 删掉 description                    FAIL=1
        FAIL  PIPL-13-01 必填字段 缺: ['description']
PASS P1-2 YAML 多一条表里没有的规则                   FAIL=1
        FAIL  规则 ID 集合不一致 仅YAML有=['PIPL-99-99']
PASS P1-3 rule_type 与表不一致                   FAIL=1
PASS P2-1 md 内容与 yaml 不一致                   FAIL=1
PASS 对照组：原始数据                               FAIL=0
```

**10 个场景，对照组必须 0 失败，其余必须 >0 失败。**

**当前覆盖范围**（诚实说明）：

| 检查项 | 有负向测试吗 |
|---|---|
| 结构 / 引文 / 表对照 / md同步 | ✅ 有 |
| **演示页 / 渲染** | ❌ **没有**（这两项靠 `check_demo.py` 与 `test_demo_render.js` 自身验证） |
| yaml_audit / 用例 / 边界 | ⚠️ 间接（改动会连带触发其他项失败） |

### 为什么规则有两份（.yaml / .md）

`yaml_audit.py` **只认 Markdown 里的 ```yaml 代码块**，而引擎要读纯 YAML。

| 文件 | 谁读 |
|---|---|
| `rules/pipl-separate-consent_v2.5.yaml` | `engine.py` |
| `rules/pipl-separate-consent_v2.5.md` | `yaml_audit.py` |

**两文件由同一份数据生成；`validate.py` 第 5 项（`md同步`）逐条比对内容，防手工改一份忘改另一份。**

### 外部依赖缺失怎么办

这两个外部依赖**默认留空**——没设环境变量就跳过对应检查，**不写死任何默认路径**，所以换机器也不会因为路径不存在而报错。

| 环境变量 | 指向 | 缺省时 |
|---|---|---|
| `COMPLIANCE_AUDIT_TOOL` | 外部 `yaml_audit.py`（法条 YAML 质量体检工具，不在本仓库） | 该项 SKIP |
| `COMPLIANCE_LAW_DOCX` | 官方个保法 docx（引文逐字交叉核对用） | 该项 SKIP |

```powershell
$env:COMPLIANCE_AUDIT_TOOL = "path\to\yaml_audit.py"
$env:COMPLIANCE_LAW_DOCX   = "path\to\个人信息保护法.docx"
python validate.py
```

**两个都缺省时**：`OK 90 / FAIL 0 / SKIP 1`；**都配齐时**：`OK 92 / FAIL 0 / SKIP 0`。

## ⚠️ 92/0/0 说明什么，不说明什么

**说明的**：规则集、`.yaml`、`.md`、Excel 核对表、GoldenCases、引擎行为、演示页数据，在当前实现下**是自洽的**。

**不说明的**：**法律判断一定正确。**

两个根本原因：

1. **GoldenCases 与规则集共享同一套假设** —— 引擎和测试可能**同错**。
   比如我认为「第 23 条要单独同意」，用例也按这个写；两边一致，但可能是错的。
2. **yaml_audit 只查结构和 quote** —— 它不知道「第 23 条该不该管这个场景」。

**准确表述**：

> **内部一致性校验通过；法律正确性仍需人工复核。**

**这也是为什么规则集必须由法律专业人士逐条确认，机器校验替代不了。**

### 还有一类盲区：**自动化测不到的浏览器行为**

92 个断言能保证「数据对、结构对、渲染不抛错」，但**保证不了「看起来对」**：

| 测不到 | 后果 | 怎么补 |
|---|---|---|
| 窄屏挤压 | 手机上左右两栏挤成一坨 | 人工在 375px 宽度看一次 |
| 颜色对比不足 | 徽章文字看不清 | 人工看 |
| focus 样式缺失 | 键盘操作时看不出焦点 | 人工 Tab 一遍 |
| 字体回退异常 | 某些系统上中文变方框 | 换台机器看 |
| 真实浏览器 JS 差异 | 我只测了 node 的 V8 | 至少用 Chrome 打开一次 |

**DOM 桩能替代的只是「逻辑对不对」，替代不了「长得怎么样」。**

## 已知限制

### 1. 引文基准：不是「必须用本仓库这份」，而是「必须有确定的那一份」

**原则**：**一字不差就行，来源不是关键。**

**但「一字不差」要先确定标准文本是哪个**。换来源可以，风险在这几处：

| 风险 | 表现 |
|---|---|
| 版本漂移 | 法律有修正，条文号会变；必须锁定到某一版本（本仓库锁定 2021-08-20 通过版） |
| 转载差异 | 「其他」vs「其它」、全角/半角标点、款次遗漏、把几条拼在一起 |
| 可审计性 | 校验失败时，要能分辨「基准错了」还是「输出错了」 |

**本仓库的取舍**：本地存一份 `data/laws/个人信息保护法.md`（版本固定、可 diff、离线可跑）。
换来源的正确做法是**一次性固定后落盘**，不是每次实时搜。

**比对标准（B 级，见 `quote_check.py`）**：

```
去除全部空白 + 全半角标点统一  →  逐字相等
```

- ✅ 容忍：空格差异、全角/半角标点、引号形态、顿号/逗号
- ❌ 不容忍：**用字差异**（「其他/其它」仍判定不一致）、漏字、改字

> ⚠️ 外部工具 `yaml_audit.py` 的 `norm()` **只去空白**，比本模块更严格。
> 本仓库的 quote 目前两种标准都能通过；若引入标点不同的转载文本，需走 `quote_check.py`。

### 2. 敏感个人信息的识别：**第 28 条给了标准，只是没做成清单**

**有对应条文。** 第 28 条第一款给了判断原则 + 举例：

> 敏感个人信息是一旦泄露或者非法使用，容易导致自然人的人格尊严受到侵害或者人身、财产安全受到危害的个人信息，
> **包括生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹等信息，以及不满十四周岁未成年人的个人信息。**

**可枚举的 7 类**（作为 `敏感个人信息类型` 的建议取值）：

```
生物识别 / 宗教信仰 / 特定身份 / 医疗健康 / 金融账户 / 行踪轨迹 / 不满十四周岁的未成年人
```

**三个陷阱**：

1. **「等」字表示非穷尽** —— 清单是举例，不是全部；不在清单里的仍可能构成敏感信息
2. **「特定身份」含义模糊** —— 实务争议大，需个案判断
3. **第 28 条第二款还有独立义务**（特定目的 + 充分必要性 + 严格保护措施）—— **本引擎未建模**

> 参考：GB/T 35273《信息安全技术 个人信息安全规范》附录 B 有更细清单，
> 但它是**推荐性国标，不是法律**，引用时须区分效力。

### 3. 三个事实的认定需外部输入

**「公开」、「境外提供」、「接收方是否为处理者」** 这三个事实，引擎只做规则判断，不做事实认定。

**补充「处理」的定义**（第 4 条第二款），供外部输入方判断「接收方是否在单独处理」：

> 个人信息的处理包括个人信息的**收集、存储、使用、加工、传输、提供、公开、删除**等。

**所以「处理」是个很宽的动作集合**——只要接收方自己会做上述任一动作，它就很可能构成独立处理者。

### 4. 内部共享场景：**引擎的结论是不完整的**

**S11 的输入前提**是：接收方为同一处理者的内部员工（不是独立处理者），因此**不适用第 23 条**。

**但这不等于没有义务。** 内部共享仍然受以下约束：

| 条款 | 要求 | 本引擎 |
|---|---|---|
| 第 13 条 | 合法性基础（内部场景常走「人力资源管理所必需」，但须「所必需」，非自动成立） | ✅ 已建模 |
| 第 17 条 | 告知 | ✅ 已建模 |
| 第 6 条 | **最小必要**：不得超出实现处理目的的最小范围 | ❌ 未建模 |
| **第 51 条** | 内部管理制度、分类管理、**合理确定操作权限**、培训、应急预案 | ❌ **未建模** |

**第 51 条第四项原文**：

> （四）**合理确定个人信息处理的操作权限**，并定期对从业人员进行安全教育和培训；

**这就是「内部共享也要留痕/控权限」的法律依据。**

> ⚠️ **因此：对内部共享场景，本引擎只会报「缺合法性基础 / 缺告知」，
> 不会报「缺操作权限管理 / 缺操作留痕」。结论不完整，不可当作完整合规意见。**

### 5. 演示页的限制

- **只能点 14 个预设场景**，不能自由输入（自由输入是 v0.2b Streamlit 的事）
- 字段仍是**人工勾选**，不是自然语言输入（那是 v0.3）
- 页面是**技术演示**，不是法律意见

### 6. 其他

- 输出为**技术评测用途**，不构成法律意见。
- 规则集的法律判断**未经专业律师逐条确认**。
